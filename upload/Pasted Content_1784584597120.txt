ACTENON THREE-REPOSITORY SECURITY, CONSISTENCY AND ADOPTION UPGRADE

You are acting as the principal security engineer and maintainer for three related repositories:

* https://github.com/Actenon/actenon-kernel
* https://github.com/Actenon/actenon-permit
* https://github.com/Actenon/actenon-cloud

Your task is to implement a tightly scoped, production-quality upgrade across all three repositories.

The purpose of this pass is to:

1. fix confirmed security and semantic weaknesses;
2. remove documentation contradictions;
3. connect Permit grants to Kernel proofs cleanly;
4. distinguish replay protection from idempotent delivery;
5. make receipt chaining enforceable by issuer policy;
6. add one credible brokered GitHub publication integration;
7. improve cross-repository conformance;
8. remove stale, misleading or unfinished production states;
9. preserve Actenon’s existing architecture rather than inventing a parallel system.

The central invariant remains:

No valid proof, no execution.

Do not build a probabilistic “trajectory monitor.”
Do not introduce a second mission-envelope format.
Do not weaken existing fail-closed behaviour.
Do not claim that Actenon prevents sandbox escape or prompt injection.
Do not replace existing active-v1 artifacts where an additive extension will work.

PHASE 2 — HARDEN KERNEL PROOF VERIFICATION

Repository:

actenon-kernel

Objective

Prevent unauthenticated forged proofs from using detailed refusal codes as a field-by-field oracle.

Required design

The verifier may perform only the minimum safe work necessary before signature authentication:

1. bounded structural parsing;
2. JSON depth and total-size checks;
3. required-field presence checks needed to resolve the verification key;
4. strict type and encoding validation;
5. safe issuer/key lookup;
6. canonicalisation of the unsigned proof;
7. signature verification.

Only after the signature is valid should it return detailed semantic failures for:

* time bounds;
* audience;
* scope;
* capability;
* intent identifier;
* tenant;
* subject;
* action;
* target;
* action hash;
* policy constraints.

Public refusal behaviour

Introduce an explicit refusal-disclosure policy.

Support at least:

public_generic
trusted_detailed
local_debug

Expected behaviour:

public_generic

For an untrusted or invalidly signed proof, return one non-oracular public result such as:

PROOF_INVALID

Do not expose whether the forged proof had the wrong:

* tenant;
* target;
* audience;
* action;
* subject;
* capability;
* expiry;
* hash.

Detailed diagnostics may still be written to a protected internal diagnostic sink, but must not be placed in public receipts, API bodies or caller-visible exception fields.

trusted_detailed

Once the proof is cryptographically authentic, permit existing detailed refusal codes such as:

* AUDIENCE_MISMATCH
* TENANT_MISMATCH
* ACTION_MISMATCH
* TARGET_MISMATCH
* PROOF_EXPIRED

local_debug

Allow full details for explicit local-development mode only. It must be impossible to enable accidentally in a production-like environment.

Important distinction

Preserve the semantic difference between:

INTENT_MISMATCH

and:

ACTION_MISMATCH

Use:

* INTENT_MISMATCH only when the signed intent_id differs;
* ACTION_MISMATCH when the bound action or action parameters differ;
* TARGET_MISMATCH when the target differs.

Update examples that incorrectly describe parameter drift as INTENT_MISMATCH.

Do not silently rename public refusal codes without a compatibility strategy.

Security tests

Add adversarial tests proving:

1. forged proof with wrong audience returns only PROOF_INVALID;
2. forged proof with wrong tenant returns only PROOF_INVALID;
3. forged proof with wrong target returns only PROOF_INVALID;
4. forged proof with expired timestamp returns only PROOF_INVALID;
5. forged proof with multiple changed fields returns the same public result;
6. validly signed but audience-mismatched proof returns AUDIENCE_MISMATCH;
7. validly signed but action-mismatched proof returns ACTION_MISMATCH;
8. validly signed but target-mismatched proof returns TARGET_MISMATCH;
9. trusted logs retain precise internal diagnostics without leaking secrets;
10. public receipts do not include untrusted forged field values;
11. key-discovery and issuer-resolution paths remain SSRF-safe;
12. malformed or oversized proofs fail before expensive cryptographic work;
13. no timing-sensitive secret comparison is changed to a non-constant-time comparison.

Document the verifier order as a security invariant.

PHASE 4 — SEPARATE REPLAY, IDEMPOTENCY AND RECONCILIATION

Primary repository:

actenon-kernel

Supporting changes may be required in:

actenon-permit
actenon-cloud

Problem

Single-use proof replay protection is not equivalent to business-operation idempotency.

An unexpected provider exception can leave this ambiguous state:

* authority consumed;
* provider operation may have succeeded;
* caller received no definitive acknowledgement;
* automatic retry risks duplication;
* automatic reissuance risks duplication.

Required model

Introduce a first-class operation identity.

Use an immutable identifier such as:

operation_id

or:

idempotency_key

The field must be bound to the exact action and included in the signed/hash-bound material.

Define behaviour:

First request

* validate proof;
* atomically claim the operation;
* execute the handler;
* pass the same operation identifier to provider adapters that support idempotency;
* record the terminal outcome;
* persist the receipt;
* mark the proof consumed.

Same operation ID and same bound action

* do not execute the handler again;
* return the recorded prior outcome or receipt;
* expose an explicit result such as:

IDEMPOTENT_REPLAY

This is not an error if the original operation completed.

Same operation ID and different action hash

Refuse:

IDEMPOTENCY_CONFLICT

Do not execute.

Unknown provider outcome

If the handler fails after dispatch and the provider outcome cannot be known:

* consume the proof;
* mark the operation:

OUTCOME_UNKNOWN

* create a durable ambiguous-outcome record;
* do not automatically retry;
* do not automatically reissue authority;
* require reconciliation.

Reconciliation interface

Create a small provider-neutral reconciliation abstraction.

It should support:

* querying by operation ID;
* resolving OUTCOME_UNKNOWN to EXECUTED or NOT_EXECUTED;
* attaching provider evidence;
* emitting a reconciliation receipt or linked outcome artifact;
* preserving the original action hash and authority reference;
* preventing resolution from changing the original requested action.

Do not create a giant workflow engine.

Atomicity and concurrency

Add concurrency tests proving:

* two simultaneous requests for the same operation execute once;
* same operation and same action return the same recorded result;
* same operation and different action refuse;
* process interruption cannot create two successful executions;
* a consumed proof cannot be reused for a different operation;
* an ambiguous result remains non-retriable until reconciled;
* reconciliation cannot be performed by an unauthorised actor;
* the receipt chain remains valid after reconciliation.

Use database transactions appropriate to each supported backend.

Document:

* at-most-once authority use;
* idempotent operation semantics;
* ambiguous provider outcomes;
* provider-specific idempotency requirements;
* reconciliation responsibility.

PHASE 5 — BIND PERMIT GRANTS TO KERNEL PROOFS

Repositories:

actenon-permit
actenon-kernel
actenon-cloud

Objective

Connect the existing Permit grant to the PCCB without inventing a new mission-envelope format.

Required artifact extension

Add a generic signed authority reference to the PCCB or its existing extension mechanism.

Preferred shape:

{
  "authority_ref": {
    "type": "actenon.permit.grant",
    "id": "grant_123",
    "digest": {
      "algorithm": "sha-256",
      "canonicalization": "ACTENON-JCS-STRICT-1",
      "value": "..."
    }
  }
}

Use existing extension/versioning conventions if they already exist.

Do not add only a bare parent_grant_id. A bare identifier is traceability, not cryptographic binding.

Security requirements

The authority reference must be:

* included in the signed PCCB payload;
* included in relevant canonical hashes;
* preserved in receipts;
* independently verifiable;
* optional for backward compatibility unless policy requires it.

At proof issuance, verify:

* the referenced grant exists;
* the digest matches the canonical grant;
* the grant is authentic;
* the grant has not expired;
* the grant is not revoked;
* the grant is not killed;
* the grant budget is not exhausted;
* the grant scope permits the action capability;
* resource selectors permit the target;
* parameter constraints permit the exact parameters;
* tenant matches;
* subject/delegate chain is valid;
* audience is permitted;
* attenuation has not escalated authority;
* required approval/evidence rules are satisfied.

At protected execution, verify the signed authority reference is structurally and cryptographically intact. Decide carefully whether live grant-state rechecking belongs at issuance, execution or both, and document the consistency/security trade-off.

Do not duplicate the full Permit decision engine inside Kernel.

Cross-repository conformance

Add conformance fixtures proving:

1. Permit canonical grant digest matches Kernel verification.
2. Valid grant → valid PCCB → successful protected execution.
3. Modified grant → digest mismatch.
4. Wrong tenant → refusal.
5. Wrong subject → refusal.
6. Capability outside grant scope → no mint.
7. Parameter outside grant constraint → no mint.
8. Expired grant → no mint.
9. Revoked grant → no mint.
10. Exhausted budget → no mint.
11. Attenuated child grant cannot exceed parent.
12. PCCB receipt records the grant reference and digest.
13. Legacy PCCBs without authority references still work where policy does not require them.
14. Policy can require an authority reference for designated capabilities.
15. The agent cannot mint or modify the authority reference.

Document the architecture clearly:

Permit decides whether authority should exist.
Kernel proves and enforces the exact action at the boundary.
Cloud operates policy, approvals, issuance and audit.

PHASE 8 — BROKERED GITHUB PUBLICATION DEMO

Repositories:

actenon-kernel
actenon-permit
actenon-cloud

Goal

Create one production-shaped example demonstrating:

* the agent cannot mint its own Permit grant or Kernel proof;
* the GitHub credential exists only inside a broker/protected endpoint;
* a valid explicitly authorised publication action succeeds;
* an unauthorised or audience-mismatched action refuses;
* a direct unprotected route is outside Actenon’s guarantee and must be blocked by deny-by-default egress;
* the example includes an offline deterministic mode and an optional real GitHub App mode.

Suggested example name

examples/brokered_github_publication/

Use repository conventions if examples are organised differently.

Scenario

A user authorises:

publish result to Slack only

or an equivalent precise permitted destination already supported by the architecture.

The agent later proposes:

create a GitHub pull request

The system must show:

1. the agent cannot access a GitHub token;
2. Permit denies the GitHub capability if the grant does not contain it;
3. no GitHub-bound PCCB is minted;
4. a Slack-bound proof cannot be reused at the GitHub endpoint;
5. the GitHub endpoint refuses before credential release;
6. no provider side effect occurs;
7. a refusal receipt is produced;
8. direct raw GitHub egress is explicitly blocked by the deployment harness or documented as a required precondition.

Avoid misleading theatre

Use correct outcomes:

* no proof at GitHub endpoint → PCCB_REQUIRED or the repository’s actual missing-proof code;
* valid Slack proof at GitHub endpoint → AUDIENCE_MISMATCH;
* GitHub action outside Permit scope → issuer refuses to mint;
* tampered GitHub action after mint → ACTION_MISMATCH;
* repeated completed operation → return idempotent recorded outcome;
* direct raw network attempt → environment egress denial, not Actenon refusal.

Do not imply Actenon intercepted network traffic it never saw.

* make no external calls;
* use a deterministic fake provider;
* prove credential non-exposure;
* record attempted provider calls;
* pass in CI;
* run with one command.

Optional live GitHub App mode

Add one genuine provider integration using a GitHub App.

Requirements:

* disabled by default;
* explicit environment variables;
* dedicated test repository;
* installation token minted only inside the broker;
* token never returned to the agent or caller;
* token redacted from logs, exceptions and receipts;
* least-privilege permissions;
* create draft pull requests only;
* bind proof to:
    * GitHub installation or account;
    * repository;
    * base branch;
    * head branch;
    * commit SHA;
    * title;
    * operation ID;
    * audience;
    * expiry;
* support provider idempotency or local operation reconciliation;
* include safe teardown instructions;
* include a dry-run mode;
* refuse to run live mode if required controls are missing.

Do not add a personal access token directly to an agent-facing process.

Tests

Prove:

* agent process environment contains no GitHub credential;
* provider token is created only after proof verification;
* invalid proof never reaches token creation;
* Permit-denied action never reaches Kernel execution;
* audience mismatch never reaches provider;
